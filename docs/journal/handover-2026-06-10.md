## The dark-theme contrast cluster — DO NOT "fix" the tokens

Bugs **8** (project button), **11** (progress-bar text), **19** (action
buttons `bg-accent`/`accent-fg`), **20** (LearningPath inactive tabs
`fg-secondary`), **21** (SetRow cards `bg-card` light), **25** ("Back to
exercise" ghost). Aster reported these persist after hard-refresh and
hypothesised the theme **token values** aren't adjusted for dark mode.

**That hypothesis is disproven with data — verified across all three
layers:**
1. **Source:** all 12 themes are imported in `main.tsx`. Dumped
   `--bg-surface`, `--accent`, `--accent-fg`, `--fg-secondary` for every
   theme — **zero anomalies**; every dark theme has a dark surface, an
   appropriate on-accent fg, and a readable secondary fg.
2. **Build:** the shipped CSS contains the correct dark overrides:
   `[data-theme=dark]{ … --bg-surface:#1c1c20; --fg-secondary:#cbd5e1; … }`
   (note: the minifier strips the quotes, so grep `[data-theme=dark]`,
   not `"dark"`).
3. **Mapping:** `.bg-card{background-color:var(--bg-surface)}` → dark in
   dark theme. Ghost buttons use `text-foreground` = `--fg-primary`
   (#ececec) = ~16:1 on the dark surface.

**Conclusion:** the tokens are correct. Editing them would regress every
theme. The cards/buttons render light in Aster's browser despite correct
CSS → the **loaded stylesheet isn't the current one**. Prime suspect: a
**stale PWA service-worker CSS cache** (Workbox precaches CSS; a
hard-refresh reloads the page but does NOT evict SW-cached assets — which
is why some of Aster's earlier reports cleared and others didn't).

**Waiting on Aster (one DevTools check settles it):** Application →
Service Workers → **Unregister** (or Clear site data) → reload. If cards
go dark → stale cache, no code change. If still light → read the
**computed `--bg-surface`** on a "white" SetRow card + the `<html
data-theme="…">` value and trace the cascade.
