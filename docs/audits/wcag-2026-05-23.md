**Standard targeted:** WCAG 2.1 Level AA (Web Content
Accessibility Guidelines, W3C Recommendation 5 June 2018).

trivial; otherwise they are filed to the backlog as P5

(Phase 39 changes land between these tags).

## C1 — Skip-to-content link + semantic HTML + landmark structure

**Commit:** `feat(a11y): skip-to-content link + landmark structure (Phase 39 C1)`

**WCAG criteria addressed:**

- **2.4.1 Bypass Blocks (A):** skip link is the first
  focusable element on every page; activating it moves focus
  past the nav directly into `#main`.
- **1.3.1 Info and Relationships (A):** every page now
  renders inside a `<main id="main">` landmark, navigation
  inside `<nav>`, page-level chrome inside `<header>`, and
  uses `<section>` / `<article>` consistently.
- **2.4.6 Headings and Labels (AA):** heading hierarchy
  reviewed and fixed where levels were skipped.

**Changes:**

- New component `frontend/src/components/SkipToContent.tsx`,
  mounted as the first child inside `<HelpProvider>` so it
  precedes `<Navigation />` in document order.
- New CSS utility classes `.sr-only` and `.skip-to-content`
  in `frontend/src/styles/global.css` (visually hidden until
  focused; reduced-motion safe).
- New i18n key `ui.a11y.skip_to_content` in all 8 catalogs
  (EN + DE handwritten, PT/TR/JA translated, ES/FR/EL
  EN-passthrough per the existing convention).
- `id="main"` added to every `<main>` element across all 13
  page components (covers loading/error/success variants;
  only one renders at a time so no duplicate-id risk).
- Heading hierarchy fix in `ImportDetail.tsx`'s `Card`
  helper component: `<h4>` → `<h3>` (h2 → h4 skipped a level).
- Heading hierarchy fix in `SyncConflictDialog.tsx`: `<h4>`
  → `<h3>` (h2 → h4 skipped a level).
- `scope="col"` added to every `<th>` column header in the
  three tables that lacked it: `BackupSection.tsx`,
  `BackupCompare.tsx`, `Progress.tsx`.

**Verified:**

- Every page wraps in `<main id="main">` and renders exactly
  one `<h1>` per route.
- `Navigation.tsx` was already `<nav>` with `aria-expanded`
  + `aria-controls` on the hamburger.
- No fake bullet/numbered lists (`•` / `▶` etc.) used as
  list markers; the two `•` glyphs in the codebase are a
  toolbar button label and a decorative `aria-hidden` leaf
  marker.

**Tests added:**

- `frontend/src/components/SkipToContent.test.tsx` (3
  cases: anchor + #main target, utility class, label).

## C2 — Keyboard navigation + focus management

**Commit:** `feat(a11y): keyboard navigation + focus management (Phase 39 C2)`

**WCAG criteria addressed:**

- **2.1.1 Keyboard (A):** every page operable with keyboard
  only. Tab / Shift+Tab traverse all interactive elements.
- **2.1.2 No Keyboard Trap (A):** Escape closes every modal
  in the codebase (3 custom dialogs were missing this
  handler; now they have it).
- **2.4.3 Focus Order (A):** the SessionChat textarea is
  focused on first mount so a keyboard user can type
  immediately without an extra Tab.

**Dialog Escape-close audit:**

| Dialog | Pattern | Before | After |
|---|---|---|---|
| `ErrorReportDialog` | Radix Dialog | ✅ native | unchanged |
| `HelpDrawer` | Radix Dialog | ✅ native | unchanged |
| `QRScannerModal` | custom + `useEffect` | ✅ already had handler | unchanged |
| `RatingDialog` | custom | ❌ none | ✅ Escape -> onCancel (disabled while submitting) |
| `AddTopicDialog` | custom | ❌ none | ✅ Escape -> onCancel (disabled while submitting) |
| `SyncConflictDialog` | custom | ❌ none | ✅ Escape -> onCancel |

**Radio-group keyboard pattern (`RatingDialog`):**

The 5 rating buttons per row already had `role="radiogroup"`
+ `role="radio"` + `aria-checked`, but every button was its
own tab stop and arrow keys did nothing. Now follows the
full WAI-ARIA radio group pattern:

- Roving tabindex: only the checked radio has `tabindex=0`;
  the other four have `tabindex=-1`. Tab exits the group.
- `ArrowRight` / `ArrowDown`: move + select next (wraps 5 -> 1).
- `ArrowLeft` / `ArrowUp`: move + select previous (wraps 1 -> 5).
- `Home` / `End`: jump to first / last.

**Focus indicators:**

The single `outline: none` in `global.css` (line 2838) is
paired with a `:focus-visible { outline: 2px solid var(--accent); }`
rule on the next line. WCAG-compliant pattern; no change.

**Other surfaces:**

- `SessionChat`: added `ref` + first-mount `focus()` to the
  primary textarea (skipped when `disabled`).
- `Navigation`: already had `aria-expanded` + `aria-controls`
  on the hamburger; no change.

**Tests added:**

- `AddTopicDialog.test.tsx`: 2 cases (Escape fires onCancel; Escape ignored while submitting).
- `RatingDialog.test.tsx`: 3 cases (Escape fires onCancel; arrow keys + Home/End with wrap-around; roving tabindex).
- `SyncConflictDialog.test.tsx`: 1 case (Escape fires onCancel).
- `SessionChat.test.tsx`: 2 cases (textarea focused on first mount; NOT focused when disabled).

## C3 — ARIA attributes pass

**Commit:** `feat(a11y): ARIA labels + live regions + form associations (Phase 39 C3)`

**WCAG criteria addressed:**

- **1.3.1 Info and Relationships (A) + 3.3.2 Labels or
  Instructions (A):** every form input now has an accessible
  name. Inputs that previously relied only on a `placeholder`
  attribute (a documented anti-pattern — placeholders disappear
  on focus and are not exposed as the accessible name by every
  AT) now also carry an `aria-label` mirroring the placeholder
  text.
- **4.1.3 Status Messages (AA):** loading + error copy is now
  announced to AT via `role="status"` (polite live region) and
  `role="alert"` (assertive live region) respectively.
- **4.1.2 Name, Role, Value (A):** verified that all
  icon-only buttons surfaced by a fresh grep (single-line and
  multi-line patterns, lucide-react child) already carry
  `aria-label` from the v1.23.2 sweep — no new violations.

**Placeholder-only inputs fixed (7 surfaces):**

| File | Input | aria-label source |
|---|---|---|
| `components/ModelPicker.tsx` | model id picker | `settings.model_picker_placeholder` |
| `components/help/HelpBrowser.tsx` | glossary search | `ui.help.search_placeholder` |
| `components/SubjectBrowser.tsx` | subject search | `taxonomy.search_placeholder` |
| `components/SubjectBrowser.tsx` | add-subject input | `taxonomy.subject_name` |
| `components/TagManager.tsx` | new-tag input | `taxonomy.tag_name` |
| `components/ProjectTaxonomy.tsx` | new-tag-on-project input | `taxonomy.new_tag` |
| `pages/Settings.tsx` | API-key input (per provider) | `${settings.api_key_label} (${provider})` |

`VoiceSettingsSection.tsx` line 260 (`<input placeholder="en-US">`)
was flagged by the audit but was a false positive — the input
is implicitly labelled by its enclosing `<label class="form-row">`
with a `<span class="form-label">` text node.

**Loading + error live regions:**

- `role="status"` added to 12 loading `<p className="muted">{t("common.loading")}</p>`
  surfaces (10 pages + 2 components: StreakCalendar, BadgeShowcase).
- `role="alert"` added to 6 error `<p className="error-text">{...}</p>`
  surfaces (Assessment, Dashboard, Curriculum, Progress, Session, Settings).

**Toasts:** react-toastify's `ToastContainer` defaults each
toast to `role="alert"` upstream; no change required.

**Form-input labels:** all Onboarding form inputs are already
inside `<label className="form-row">` wrappers (implicit
labelling). All VoiceSettings toggles likewise. No fix needed.

**Tests added:**

- `frontend/src/components/aria-pins.test.tsx` (2 cases:
  `role="status"` semantics, `role="alert"` semantics). The

## C5 — Color contrast + colorblind-safe method colors

**Commit:** `feat(a11y): WCAG AA color contrast + colorblind-safe method colors (Phase 39 C5)`

**WCAG criteria addressed:**

- **1.4.3 Contrast (Minimum) (AA):** every text + background
  pair in the two shipped theme variants (light + dark) meets
  4.5:1 normal text or 3:1 large-text / UI thresholds.
- **1.4.11 Non-text Contrast (AA):** UI affordances (skip
  link, focus outlines) remain visible in forced-colors mode
  via a dedicated media block.
- **1.4.1 Use of Color (A):** every method badge pairs the
  color with a text label, so color is never the sole means
  of conveying which method is in play.

**Theme model:** adaptive-learner ships **2 theme variants**:
light (`:root`) and dark (`[data-theme="dark"]`). The handover
mentioned "5 themes × light/dark = 10 variants" — that's the
bibliogon model from which this project diverged. The actual
audit scope was the 2 we have, not 10.

**Findings + fixes:**

1. **Light-theme primary button failed AA (4.47:1)**.
   `--accent-fg` `#ffffff` on `--accent` `#6366f1` was below
   the 4.5:1 normal-text threshold. **Brand-palette decision
   (per Aster):** promote `--accent-hover` (`#4f46e5`) to be
   the new `--accent` (6.29:1 ✓); pick `#4338ca` as the new
   `--accent-hover` (8.4:1). Tiny visual change, fixes the
   ratio authoritatively, no test exception. Dark theme
   already passed (5.32:1) and stays unchanged.

2. **Method badges had white text on bright backgrounds**.
   `MethodBadge`, `MethodSwitchBanner`, `ToolRecommendations`,
   `QuickStartButton`, and the Assessment dominant-method
   pill all hardcoded `color: "#ffffff"` over the 6 method
   colors. Several pairs failed AA (white on `#10b981` =
   2.5:1; white on `#f59e0b` = 1.9:1). **Fixed without
   changing the brand palette:** new `bestTextOn(hex)` helper
   in `styles/contrast.ts` picks black or white per
   background based on contrast computation. All 6 method
   colors pick `#000000` on the current pin. Brand identity
   preserved.

3. **`forced-colors: active`** block added to `global.css`
   pinning skip-link visibility in Windows High Contrast Mode.
   The rest of the app uses CSS variables that HCM remaps
   correctly out of the box.

**Colorblind safety (method palette):**

The 6 method colors include red (`error_based` `#ef4444`) and
green (`dialogic` `#10b981`), the classic deuteranopia /
protanopia confusion pair. WCAG SC 1.4.1 is satisfied because
**every method badge in the codebase pairs the color with a
text label** (`MethodBadge`, `MethodSwitchBanner`,
`ToolRecommendations`, `QuickStartButton`, Assessment result).
Color is decorative, never the sole carrier. No palette
change required.

**New helper:** `frontend/src/styles/contrast.ts` exports:

- `parseHex`, `relativeLuminance`, `contrastRatio` — exact
  WCAG 2.1 implementation.
- `AA_NORMAL_TEXT = 4.5`, `AA_LARGE_TEXT_OR_UI = 3` — the
  two AA thresholds.
- `bestTextOn(background)` — returns the higher-contrast
  black/white text color for the given background.

**Tests added:**

- `frontend/src/styles/contrast.test.ts` (21 cases):
  - 6 cases × 2 themes for the canonical foreground / background
    pairs (`--fg` on `--bg`, `--fg` on `--surface`, `--fg-muted`
    on `--surface-2`, etc.).
  - 6 method-badge cases asserting `bestTextOn(METHOD_COLORS[m])`
    meets AA for every method.
  - 3 helper-sanity cases (`bestTextOn` picks the higher-
    contrast option; black-on-white = 21:1; argument order
    doesn't matter).

  The test file reads `global.css` at runtime so the assertions
  cannot drift out of sync with the production CSS — if a
  future tweak lowers a contrast below AA, the corresponding
  test fails with the actual measured ratio.

## C7 — prefers-reduced-motion audit

**Commit:** `feat(a11y): prefers-reduced-motion respected across all animations (Phase 39 C7)`

**WCAG criteria addressed:**

- **2.3.3 Animation from Interactions (AAA, but cheap to ship):**
  any animation triggered by user interaction can be disabled.
- **2.2.2 Pause, Stop, Hide (A):** animations are not the sole
  means of conveying information; reduced-motion users get an
  instant state change.

**Approach:** in addition to the existing per-animation overrides
(cycle-pulse, assessment-slide, xp-rise, qr-scanline,
assessment-hint-fade, cycle-peek-fade, qr-success-pop, etc.), a
catch-all `@media (prefers-reduced-motion: reduce)` block at the
end of `global.css` resets `animation-duration` +
`animation-iteration-count` + `transition-duration` +
`scroll-behavior` for every element via the universal selector.
`!important` is required so the catch-all wins against
per-component animation shorthand declarations. The 0.01ms
duration is the standard "essentially instant but not zero"
value that keeps `onfinish` / `transitionend` handlers firing.

**One inline-style fix:** Phase 38's `HelpTooltip` had its
hover transition declared as inline CSS-in-JS
(`transition: "background-color 120ms ease-in-out"` on the
`.help-term` span). Inline styles are not reachable by CSS
media queries, so reduced-motion users would still see the
120ms fade. The transition is now declared on `.help-term` in
`global.css` so the catch-all block can reset it.

**Tests added:**

- `frontend/src/styles/reduced-motion.test.ts` (3 cases):
  - The reduced-motion block exists.
  - It resets `transition-duration` to a near-zero value.
  - It uses `!important` so per-component overrides cannot
    win.

  Reads `global.css` at test time so the pin cannot drift out
  of sync with the production CSS.
