# Adaptive Learner v1.25.0

**Released**: 2026-05-23

Phase 41 — identity persistence in the config directory + a
browser-wipe recovery flow + a Settings Danger Zone with
three-step typed-confirmation reset. Six atomic commits, two
new backend endpoints, one Settings panel + one Settings
section, 13 new i18n keys across 8 catalogs.

The motivation: until v1.24.x, clearing browser data
(localStorage, cookies, IndexedDB) silently lost the
"who am I" pointer that ties the user to their backend
data. The data itself survived in SQLite (API mode); the
app couldn't find the user. v1.25.0 closes that gap with a
two-layer recovery (API mode reads a config file, Dexie
mode self-recovers from IndexedDB) and pairs it with a
proper Danger Zone for the inverse situation: "I want to
actually wipe everything."

## What changed

### A — Backend identity persistence (commit `8803020`)

New ``backend/app/services/identity_service.py``:

- Writes a small YAML at
  ``~/.config/adaptive_learner/identity.yaml`` carrying
  ``user_id``, ``active_project_id``, ``language``, and
  ``last_seen``. Same dir + perms (0o600) as
  ``secrets.yaml``.
- ``update_identity`` is a merge-style writer: partial calls
  preserve fields they don't pass (so a language-only
  update keeps active_project_id intact).
- Hooked into ``services/users.py::create_user`` +
  ``update_user`` (language change) and
  ``services/projects.py::create_project`` + ``update_project``
  (when ``active=true`` is being set). Hooks run AFTER the
  DB commit and swallow filesystem errors so a config-write
  failure cannot bubble a 500 to an API call whose DB
  change already landed.

Two endpoints in ``backend/app/routers/identity.py``:

- ``GET /api/identity`` → 200 ``IdentityOut`` or 404
  when no file. The recovery channel for API-mode Landing.
- ``DELETE /api/identity`` → 204; idempotent file delete.
  (The Danger Zone path uses the bigger ``POST /api/reset``
  in 41F; this is kept as a smaller building block.)

Test isolation: ``conftest.py`` now sets
``ADAPTIVE_LEARNER_CONFIG_DIR`` to a per-process tmp dir,
paralleling the existing ``ADAPTIVE_LEARNER_DATA_DIR``
isolation. Without this, every test exercising create_user
or create_project would silently write to the contributor's
real ``~/.config/adaptive_learner/`` — the exact bug class
the production-marker tripwire was designed to prevent.

### B — Frontend recovery flow (commit `97d72fa`)

``frontend/src/pages/Landing.tsx`` gains a recovery branch
that runs when localStorage is empty (or after a 404 wipes
a stale userId):

- ApiStorage: calls ``api.identity.get()`` → re-seeds
  localStorage + redirects to Dashboard silently. Per the
  "Recovery is invisible" rule, no toast.
- DexieStorage: queries the most recent ``users`` row +
  its active ``learningProjects`` row from IndexedDB →
  re-seeds + redirects + shows a friendly toast: "Welcome
  back! Your learning data is still here." (DE:
  "Willkommen zurück! Deine Lerndaten sind noch da.").

Unified surface: new ``IUsersNamespace.findMostRecent``
returns ``RecoveryHint | null`` — Landing.tsx is
mode-agnostic, only the toast decision branches by mode.

### C — DEFERRED: BACKUP-DIR-EXPORT-01 (commit `fe426ba`)

The original Phase 41C ambition — auto-backup of Dexie
storage to ``~/.config/adaptive-learner/backup-latest.json``
via the File System Access API — was filed to the backlog
as ``BACKUP-DIR-EXPORT-01`` (P3) after the Phase 41 audit
showed browser sandboxing makes silent writes to an
arbitrary user-readable path infeasible. Two-layer
recovery (identity.yaml + Dexie self-recovery) covers ~95%
of real-world scenarios; the follow-up is an *interactive*
"Save backup to disk" Settings action with a different UX
shape. Trigger: a user reports losing data after a full
browser-data clear in Dexie mode.

### D — Settings > About > Identity panel (commit `420ff9c`)

Pure read-only diagnostic surfacing the identity file's
path, status (Active / Not found), and last-updated
timestamp. New ``GET /api/identity/status`` endpoint that
always returns 200 (different from ``GET /api/identity``
which 404s — the status endpoint always succeeds so the
UI can show a "Not found" badge alongside the resolved
path even before the file gets written).

API mode only: the parent ``AboutTab`` gates the section on
``storageMode === "api"`` since Dexie mode has no
backend-side identity file.

### F — Settings > Danger Zone (commit `6a1affa`)

Red-bordered section at the bottom of the Settings page
with a three-step typed-confirmation reset:

1. Idle pane: always-visible "Create backup first?" offer +
   a single red "Reset Everything" button.
2. Confirmation modal: full warning text + Cancel /
   Continue.
3. Typed-confirm pane: text input + a red "Delete
   permanently" button. The button is disabled until the
   input equals the literal string "RESET" — lowercase,
   partial, and trailing-whitespace inputs all stay
   disabled.

Backend (``POST /api/reset {confirmation: "RESET"}``):

- Truncates every table in ``Base.metadata.sorted_tables``
  reverse order.
- Removes ``identity.yaml``.
- Scrubs the ``ai.*`` block from ``secrets.yaml``,
  **preserving** the top-level ``secret_key`` Fernet field
  — deleting it would make any surviving encrypted data
  unreadable forever; the surviving backup-restore path
  depends on it.
- Returns ``{reset: true, tables_cleared: N}``.

Dexie mode mirrors the contract locally: same token gate
(throws ``ApiError(400)`` for parity), clears every Dexie
store + the auto-backup ring, no backend call.

After a successful reset the UI clears localStorage +
sessionStorage on its own (browser-key stores are
UI-owned), shows a success toast, and navigates to Landing.

13 new ``settings.danger_zone_*`` i18n keys: native DE +
EN + native PT / TR / JA (per the project's Phase 26
strict-translation tier); ES / FR / EL stay EN-passthrough
(audit allows).

## Migration

No database schema changes. No new production runtime
dependencies. No frontend bundle-size change worth
mentioning.

**New file on disk after first user creation**:
``~/.config/adaptive_learner/identity.yaml`` (0o600,
auto-managed). Safe to delete; the app will recreate it.

**Existing dev databases** continue to work. The four hook
sites where ``update_identity`` runs (POST /users, PATCH
/users, POST /users/.../projects, PATCH /projects/.../{active}=true)
are best-effort: a config-write failure does NOT roll back
the legitimate DB change.

**Plugin packages**: all 10 plugins now use the
``importlib.metadata`` derivation pattern uniformly
(brought into Phase 40 alignment in v1.24.1); identity
changes ship without touching the plugin tree.
