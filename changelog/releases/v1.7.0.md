# Adaptive Learner v1.7.0

**Released**: 2026-05-20

Phase 20 — **QR-Code Camera Scan for Sync Pairing.** v1.0.0
shipped paste-the-link pairing; v1.7.0 closes the loop with
native camera-based QR scanning on mobile. The desktop side
(QR generation) is unchanged. This release is purely about the
PHONE side reading the QR with the camera, plus a file-upload
fallback for browsers where live camera access is unavailable
or blocked.

Backlog BL-04 is closed by this release.

## Added

### 20A — QR scanner library + camera access

- New ``html5-qrcode@2.3.8`` (exact pin) frontend dependency.
  Picked over ``jsQR`` because it bundles cross-browser
  ``getUserMedia`` plumbing and the QR decoder in one library
  with a single TypeScript-friendly entry point.
- New ``frontend/src/components/sync/QRScanner.tsx`` wraps
  ``Html5Qrcode`` with the Adaptive-Learner-specific
  concerns:
  - Requests the rear camera (``facingMode: "environment"``)
    on mount; cancels cleanly if the component unmounts
    while the permission prompt is still up.
  - Stops all media tracks on unmount AND on successful scan
    AND on cancel — no zombie camera. Defensive sweep covers
    older iOS Safari where the library's own ``stop()`` has
    been observed to leak a track.
  - Validates every decoded text against
    ``parsePairingUri``; invalid content fires
    ``onInvalidQr`` and keeps scanning so the user can
    re-aim. Valid content fires ``onSuccess`` exactly once
    even if the library reports multiple matches.
  - Permission / no-camera / init failures land on
    ``onError`` with a typed ``code`` so the parent can
    render an actionable hint.

### 20B — Sync Settings integration

- New ``frontend/src/components/sync/QRScannerModal.tsx``:
  overlay wrapper with dark backdrop, close button +
  Escape-to-close + backdrop-click-to-close, body-scroll
  lock (prevents iOS from scrolling the camera preview
  off-screen), and three internal panels — scanning, error,
  success.
- ``SyncSection.PhoneUnpairedView`` is mobile-first: "Scan
  QR Code" is the primary CTA up top; "Or paste the link
  manually" sits inside a collapsed ``<details>`` element.
  Desktop users on the same view can expand the details if
  they prefer paste.
- The scanned URI routes through the existing
  ``getSyncEngine().pair`` — identical to the paste-the-link
  pipeline. On pair failure (expired token, invalid token,
  network) the modal stays open so the user can scan a fresh
  QR from the desktop.

### 20C — File-based QR scan fallback

- New ``frontend/src/components/sync/QRImageUpload.tsx``:
  ``Html5Qrcode.scanFile`` wrapper. Tap "Upload QR image",
  pick a screenshot from the gallery / file system, the
  library decodes the QR, the result is validated, the
  success path is identical to the camera scan.
- Wired into ``QRScannerModal`` in two places:
  1. **Below the live scanner**: "No camera? Take a
     screenshot…" prompt with the upload button. Always
     available.
  2. **Inside the error panel** when camera-init fails
     (permission-denied, no-camera, init-failed) — one-tap
     path forward without falling back to the paste-the-link
     surface.
- Covers in-app browsers, older iOS PWAs, desktop machines
  without a webcam, and users who deny camera permission
  but still want to pair.

### 20D — Camera UX polish

- Viewfinder overlay over the camera preview: four corner
  brackets framing a 60%-of-frame cutout + an animated
  horizontal scan-line. Pointer-events: none so it never
  intercepts a tap.
- Haptic feedback on successful scan via
  ``navigator.vibrate?.(50)``. ``?.`` covers desktop / iOS
  Safari; try/catch covers Feature-Policy-gated browsers.
  Vibration is a confirm signal, NOT an animation — it's
  not suppressed by prefers-reduced-motion (users disable
  haptics OS-side).
- Success checkmark gets a 320ms pop animation.
- ``@media (prefers-reduced-motion: reduce)`` suppresses
  both the scan-line sweep and the checkmark pop. Corner
  brackets stay (they're decorative-not-animated and
  convey the viewfinder intent even with motion off).
- All CSS lives in ``frontend/src/styles/global.css`` under
  the existing ``@keyframes`` block convention. No CSS
  modules, no styled-components.

## Notes

- The desktop QR-code generation surface
  (``DesktopUnpairedView`` in SyncSection) is unchanged. The
  v1.0.0 desktop -> v1.0.0 phone pairing still works.
- Camera permission is requested ONLY when the user clicks
  "Scan QR Code", never on page load.
- The image-upload fallback works for both mobile and
  desktop. A desktop user with two machines can screenshot
  the QR on machine A and upload it on machine B without
  ever invoking ``getUserMedia``.
- ``parsePairingUri`` (the existing v1.0.0 URI parser) is
  the single source of truth for what counts as a valid
  pairing URI. Both the camera path and the upload path
  route through it, so they share the same validation logic
  and the same "Not a valid pairing code" message.

No breaking changes. The existing paste-the-link surface
stays available inside the ``<details>`` element so anyone
with a workflow that pastes the link unchanged.

frontend swap.
