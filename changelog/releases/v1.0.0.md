# Adaptive Learner v1.0.0

**Released**: 2026-05-20

Phase 13 — **Local-network sync with AI-merge**. Adaptive
Learner reaches 1.0 with the feature that ties the desktop and
PWA halves together: bidirectional sync between two devices on
the same WiFi, opt-in (the user clicks Sync Now), and intelligent
conflict resolution that escalates to the configured AI provider
on request.

## Added

### 13A — Sync protocol + backend

- New `backend/app/services/sync_service.py` + `pairing.py` +
  router `backend/app/routers/sync.py` mounted at `/api/sync/*`.
- 14-table sync surface:
  - **Append-only** (idempotent insert; skip if id exists):
    `learning_sessions`, `session_messages`, `session_ratings`,
    `session_notes`, `progress_commits`, `method_switches`,
    `step_evaluations`.
  - **Mutable** (compare `updated_at` against the client's
    `since`; flag a conflict iff both sides changed):
    `users`, `user_settings`, `learning_projects`,
    `learning_profiles`, `curriculums`, `learning_topics`,
    `lessons`.
- Each table carries a `scope` ("self", "direct",
  "via_curriculum", "via_project", "via_session") so the
  `_scoped_query` helper JOINs through the right parent. Child
  rows (e.g. `session_messages`) scope through
  `LearningSession → LearningProject` rather than direct
  `user_id`.
- Endpoints:
  - `GET  /api/sync/status?user_id=` — per-table row counts.
  - `POST /api/sync/push`            — apply records, return
    conflicts.
  - `POST /api/sync/pull`            — stream records newer
    than `since`.
  - `POST /api/sync/resolve`         — apply user's conflict
    decisions.
  - `POST /api/sync/pair/generate`   — mint a 5-min one-time
    token (returns 201 + 32-hex token + expiry).
  - `POST /api/sync/pair/verify`     — consume the token,
    return the user info.
- Pairing tokens live in a thread-safe in-memory store with
  128-bit entropy + 5-minute TTL + one-time-use. Restart
  invalidates all tokens (acceptable).

### 13C — Sync engine

- New `frontend/src/storage/sync-engine.ts`:
  - `SyncEngine.pair(uri)` parses
    `adaptive-learner://sync?host=X&port=Y&token=Z`, verifies
    the token, persists the config (host, port, user_id,
    user_name, paired_at) in localStorage.
  - `SyncEngine.sync(resolver?)` runs the full push → resolve
    → pull → stamp flow against the 12 sync-tracked Dexie
    tables.
  - `SyncEngine.unpair()` clears config + last-sync + history.
  - `SyncEngine.ping()` health-probes the remote backend.
- 5-entry rolling sync history persisted alongside the config
  for the Settings panel.
- AbortController + 8-second per-fetch timeout. In-flight
  gate rejects parallel sync calls with HTTP 409.
- `step_evaluations` and `session_notes` are out of scope for
  v1.0.0 sync — the Dexie `step_evaluations` row carries
  `suggested_step`/`duration_seconds`/`created_at` fields the
  backend `evaluated_at`/`to_step` shape doesn't match; clean
  field-mapping is v1.1 work.

### 13B — QR-code pairing

- New dependency: `qrcode@1.5.4` (pinned, ~36 KB) for desktop-
  side QR rendering.
- Pairing flow:
  - Desktop ("Generate pairing code"): POSTs to
    `/api/sync/pair/generate`, renders the resulting token in
    both a QR code and a `adaptive-learner://` paste-the-link
    string with a Copy button + 5-minute expiry indicator.
  - Phone ("Connect"): textarea accepts the pasted link, calls
    `SyncEngine.pair()`. No camera permission required — this
    is the path that ships in v1.0.0.
- Camera-based QR scanner is a noted v1.1 enhancement; the
  paste-the-link UX is robust on every device and avoids the
  ~70 KB scanner bundle weight + permission UX complexity.

### 13D + 13E — Conflict resolution + AI-assisted merge

- New `SyncConflictDialog` component with one row per
  conflicting record:
  - Side-by-side local vs remote columns with changed fields
    highlighted (orange background).
  - Radio choice per row: **Keep this device** / **Keep
    other device** / **Merge manually**. Default = "remote"
    (the user just initiated sync — remote is what they're
    pulling in).
  - Manual merge: per-field editor with text / number /
    boolean inputs. `id`, `*_at`, `user_id` stay read-only.
- **Smart Merge** (Phase 13E): only renders when an AI
  provider with a valid API key is configured. Sends both
  versions to the AI with a strict-JSON merge prompt; parses
  the response with the same defensive shape used elsewhere
  (fence-strip + first-block extract + type guards); force-
  preserves the original `id` even if the AI rewrites it. The
  merged result lands in the editor — the user reviews and
  explicitly clicks Apply. AI never writes data without
  confirmation.

### 13F — Settings sync panel

- `<SyncSection />` appended to Settings:
  - Unpaired in API mode: host/port inputs (defaulting to
    `window.location.hostname` + `18001`) + "Generate pairing
    code" button.
  - Unpaired in Dexie mode: paste-the-link textarea +
    Connect button.
  - Paired: connection card (host, port, user_name,
    paired_at), Sync Now button, Unpair (with confirmation),
    last-sync timestamp, 5-entry sync history with ✓/✕ per
    run + summary.

### 13G — Navigation sync indicator

- New `<NavLink to="/settings">` with a status icon:
  - ⇄ when paired
  - ○ when unpaired
- Title + aria-label carry the state. Re-reads localStorage
  on tab focus + route change so a pair/unpair done in
  another tab updates the badge.

## Notes & deployment scenarios

- **Sync is always opt-in.** Never automatic. The user clicks
  Sync Now.
- **Append-only data auto-merges.** No user interaction.
- **Mutable data always confirms.** User sees the conflict
  before any overwrite.
- **AI merge is a SUGGESTION.** User confirms. AI never
  writes data without approval.
- **Pairing is local-network only.** No cloud relay. No
  internet required (except for AI merge calls when Smart
  Merge is used).
- **Mixed-content constraint.** Browsers block an HTTPS PWA
  page from fetching `http://192.168.1.x:port` resources. The
  feature works in:
  - Local dev (both sides at localhost)
  - Self-hosted desktops (PWA installed from the desktop's
    own HTTP origin)
  - Any future deployment where both sides share an origin
    or are both HTTPS
- **UUIDs prevent ID collisions.** UUIDv4 across all primary
  keys (in place since v0.0.2). After pairing both devices
  share the same `user_id`.
