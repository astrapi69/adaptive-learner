# Adaptive Learner v1.72.1

Patch release — **dark-theme button-background fix + accessibility fixes,
both surfaced by the v1.72.0 visual-regression and axe-core suites once
they actually ran end-to-end**. Frontend + test-infrastructure only; no
schema, API, or data-model changes.

## Fixed — dark theme

- **Raw `<button>` showed the UA `buttonface` background in dark themes
  (#271).** With Tailwind preflight off, a raw `<button>` carrying no
  explicit `background-*` inherited the browser's `buttonface` system
  colour (~`#efefef`). Because that colour follows `color-scheme: light`,
  it was theme-independent — a glaring near-white box with invisible light
  text on all 6 dark themes (LearningPath `SetRow`, the "Nicht
  heruntergeladen" section, Dashboard project cards). This was the
  unfinished half of the v1.71.0 `#185` fix, which added
  `button { color: inherit }` but no background. The same base-layer rule
  now also sets `background-color: transparent`; it loses to any explicit
  `bg-*` utility and to component classes, so shadcn `<Button>` variants and
  intentionally-styled buttons are untouched. `contrast.test.ts` pins both
  halves.

## Fixed — accessibility (axe-core, WCAG 2 A/AA)

- **Five serious axe violations resolved (#273).** With the audit harness
  fixed (below) the suite found and now passes zero violations on all 7
  audited routes:
  - `aria-progressbar-name`: the DailyMissionsCard mission bars and the
    XPWidget level bar had no accessible name — both now carry an
    `aria-label`.
  - `nested-interactive`: `ProfileRadar` put `role="img"` on a wrapper that
    also held the interactive `ChartSummary` (a focusable `<summary>`);
    `role="img"` + the aria-label moved to the chart-only inner element.
  - `listitem`: the Content "Knowledge" domain groups rendered `<li>` set
    rows directly under a `<div>`; they are now wrapped in a `<ul>` like the
    language sets.
  - `color-contrast` on `/learning-path`: resolved by the `#271` fix.

## Fixed — test infrastructure

- **Visual-regression `lesson-matching` view never baselined (#270).**
  Inside a lesson `MatchingExercise` renders `controlled`, so its internal
  `matching-submit` button is absent — submission runs through the shared
  `lesson-check`. The visual helper waited for `matching-submit` and timed
  out on all 12 themes, so the view had no baseline. The helper now drives
  the check via `lesson-check`. First committed baseline lands here (5
  views × 12 themes = 60 screenshots, dark themes now correct).
- **axe-core a11y suite never ran (#272).** `@axe-core/playwright` rejects a
  page created with `browser.newPage()` ("Please use
  `browser.newContext()`"), so the serial suite (`#247`) aborted on the
  first route and audited nothing. The audit page is now created from an
  explicit `browser.newContext()`.
