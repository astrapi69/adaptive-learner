# Adaptive Learner v1.20.0

**Released**: 2026-05-22

Phase 34 — **secrets.yaml API-Key Storage for Desktop Mode**.
The desktop launcher use case now has a file-based key
configuration path alongside the existing Settings-UI flow.
Three-layer precedence with the AI provider plugins resolving
through the chain transparently.

## Added

### File-based API key configuration

A new `~/.config/adaptive_learner/secrets.yaml` overlay sits
between env vars and the Fernet-encrypted DB column. Bibliogon-
parity loader pattern (the scaffolding was already in place from
the v1.0.0 cleanup — see commit `0db2257`); v1.20.0 populates
the previously-empty `_ENV_SECRET_OVERRIDES` map with the three
provider entries plus `default_model` overrides, and adds the
resolver, template, and permission audit on top.

```yaml
# ~/.config/adaptive_learner/secrets.yaml
ai:
  anthropic:
    api_key: "sk-ant-..."
    default_model: "claude-sonnet-4-20250514"  # optional override
  openai:
    api_key: "sk-..."
  gemini:
    api_key: "AIza..."

# secret_key: "..."  # Fernet encryption key (also reads env var)
```

### Key resolution chain

For every `get-API-key` call across the plugin layer, the AI
orchestrator now walks (highest priority wins):

1. **Environment variable**:
   `ADAPTIVE_LEARNER_{ANTHROPIC,OPENAI,GEMINI}_API_KEY` /
   `..._DEFAULT_MODEL`.
2. **secrets.yaml**:
   `ai.<provider>.api_key` / `ai.<provider>.default_model`.
3. **Database** (UserSettings via the Settings UI):
   Fernet-decrypted `api_key_<provider>` /
   `model_override_<provider>`.
4. **None** — the AI call returns an error asking the user to
   configure a key somewhere.

Per the v1.20.0 design decision, `secrets.yaml` beats the UI
`model_override` (power-user file config wins over UI for the
desktop launcher use case). Env vars always beat both.

### Template auto-generation + permissions

`backend/app/services/secrets_template.py`:

- `ensure_template_exists()` writes a fully-commented template
  on first run with all keys commented out + `chmod 0600` on
  POSIX. Idempotent; non-fatal on write failure.
- `audit_permissions()` logs a `WARNING` if the file is
  group/world readable; no-op on Windows.

Both run once at module-import time (skipped under
`ADAPTIVE_LEARNER_TEST=1` so test runs don't touch the
developer's real config dir).

### Settings UI per-provider source badge

`UserSettingsOut` gains a new `ApiKeySource` enum
(`env | secrets_yaml | settings | none`) on three new fields
(`key_source_anthropic`, `key_source_openai`,
`key_source_gemini`). The Settings page renders:

- A badge: "Key from: secrets.yaml" / "Key from: environment" /
  "Key from: Settings" / "No key configured".
- An info banner with the file path or env-var name when the
  key is externally managed.
- Save + Remove + input fields disabled when externally managed
  — editing happens at the file/env level.
- The active-provider "missing key" warning is suppressed when
  the field is externally managed (the banner replaces it).

In Dexie / PWA mode every source collapses to `"settings"` or
`"none"` (browser sandbox has no filesystem access).

### Migrated all plugin callers to `resolve_api_key`

Six call sites (`backend/app/routers/settings.py`,
`backend/app/routers/imports.py`, plugins anki, session ×2,
notebooklm) switched from `get_decrypted_api_key` (DB-only) to
the new `resolve_api_key` resolver. `get_decrypted_api_key`
stays as the DB-only primitive for tests and edge cases.

## Design decisions

Three interpretation questions surfaced before implementation
and confirmed by the user:

- **Q1 (`_ENV_SECRET_OVERRIDES` shape)**: kept the existing
  `dict[env_var, tuple[path...]]` shape that already housed
  the `_ENV_CONFIG_SOURCES` map. Spec's inverted notation
  would have been equivalent but inconsistent with the
  established codebase pattern.
- **Q2 (`default_model` precedence)**: secrets.yaml beats
  `UserSettings.model_override`. Power users who edit files
  expect file-level config to win over UI.
- **Q3 (Fernet `secret_key` fallback)**: kept fail-hard if
  `ADAPTIVE_LEARNER_SECRET_KEY` is unset. Silent generated
  defaults would have meant different keys per dev machine
  and across container restarts, silently corrupting the
  encrypted DB rows. secrets.yaml `secret_key:` works
  transparently via the existing `_hydrate_env_from_config`.

## Upgrade notes

- **Existing installations**: no migration required. The new
  resolver falls through to the existing Fernet-encrypted DB
  column when neither env vars nor secrets.yaml carry a key,
  so previously-configured Settings-UI keys keep working
  unchanged.
- **Desktop launcher users**: a fresh `~/.config/adaptive_learner/secrets.yaml`
  template is auto-created on first start. Uncomment + fill in
  the keys you want; restart the backend. The Settings UI
  surfaces the new "Key from: secrets.yaml" badge once the
  resolver picks the file value.
- **Docker / CI**: env vars still preferred for orchestrator-
  injected secrets. The `ADAPTIVE_LEARNER_{PROVIDER}_API_KEY`
  + `ADAPTIVE_LEARNER_{PROVIDER}_DEFAULT_MODEL` names are new;
  set whichever you need.
- **Power users with rotated `ADAPTIVE_LEARNER_SECRET_KEY`**:
  unchanged — the Fernet key still fails hard if unset. Either
  export the env var or set `secret_key:` in secrets.yaml.
