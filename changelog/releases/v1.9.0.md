# Adaptive Learner v1.9.0

**Released**: 2026-05-21

Phase 22 — **Global Subjects and Tags.** Cross-project organisation
arrives: every LearningProject can now be classified by a global
Subject (hierarchical taxonomy, pre-seeded with 80+ nodes across 8
top-level categories) and tagged with per-user labels (free-form,
colour-coded). Both surfaces ship full CRUD, a Dashboard filter
bar that scopes the per-project widgets to a matching set, and an
Onboarding suggestion step that proposes subjects + tags as the
user types in the Topic field.

## Added

### 22A — Subject + Tag data models

- **Subject**: global, hierarchical (parent_id self-FK, SET NULL
  on parent delete). Same tree pattern as LearningTopic but
  cross-user — every device's taxonomy converges on the same
  shape via the new sync ``global`` scope.
- **Tag**: per-user, unique on (user_id, name), optional hex
  colour for badge rendering. Cascades on user delete.
- **ProjectSubject / ProjectTag**: M:N association tables with
  unique pair constraints; assigning the same subject/tag twice
  is a no-op. Cascade with the project.
- Alembic 0008 + Dexie schema v6 + sync surface (4 new entries:
  ``subjects`` MUTABLE + ``global`` scope, ``tags`` MUTABLE +
  ``direct`` scope, ``project_subjects`` + ``project_tags``
  APPEND-ONLY + ``via_project`` scope).
- Sync-surface audit pinned to 20 tables (was 16). Backup audit
  same.

### 22B — Subject seed data

- ``backend/config/seed/subjects.yaml`` ships 80+ pre-seeded
  Subject nodes across 8 top-level categories: Languages,
  Mathematics, Programming, Sciences, Music, Humanities, Social
  Sciences, Skills. Tree depth up to 3 levels (e.g. Languages >
  Spanish > Grammar).
- Slug-keyed idempotent loader: re-running the seed never
  duplicates; user-added custom subjects survive every restart.
- Fires from the FastAPI lifespan AFTER ``init_db()``; seed
  failure logs but does NOT block startup.
- DE display names ship for every top-level category and every
  language node + most sub-categories.

### 22C — CRUD routes

Backend:

- ``/api/subjects`` (list, get, create, patch, delete)
- ``/api/users/{user_id}/tags`` (list, create)
- ``/api/tags/{tag_id}`` (patch, delete)
- ``/api/projects/{id}/subjects`` (list, assign, unassign)
- ``/api/projects/{id}/tags`` (list, assign, unassign)

Tags use the path-prefix user-scoping pattern. Subjects are
global (no user prefix). Assignment is idempotent; duplicate
tag-name within a user is a clean 409 conflict; cross-user tag
assignment to a project is rejected with 400.

Frontend mirror:

- ``api.subjects``, ``api.tags``, ``api.projectTaxonomy``
  namespaces in ``api/client.ts``
- ``IStorageService`` extended with ``ISubjectsNamespace``,
  ``ITagsNamespace``, ``IProjectTaxonomyNamespace``
- ApiStorage thin pass-through; DexieStorage implements the full
  contract against the v6 schema, including SET-NULL-on-parent-
  delete, cascade of associations on tag/subject delete, and the
  cross-user-tag rejection.

### 22D — Frontend components

- **SubjectBrowser**: tree view via the TypedTreeNode adapter,
  case-insensitive search that keeps the ancestor path visible,
  inline "Add Custom Subject" at the root and per-row "+ child"
  affordances, optional ``onSelect`` for click-to-filter use
  cases, ``readOnly`` mode for display-only contexts.
- **TagManager**: per-user list with colour-picker badges,
  inline create / rename / colour edit / delete-with-confirm,
  multi-select via ``selectedTagIds`` + ``onToggleSelected``,
  ``readOnly`` mode.
- **ProjectTaxonomy**: per-project assignment surface — chip-
  list of assigned Subjects with × remove buttons, chip-cloud of
  all user tags (faded when unassigned, opaque + selected when
  assigned), one-click toggle, and a "create + assign in one
  flow" form for new tags. The Subject picker mounts
  SubjectBrowser inline.

### 22E — Dashboard filtering

- **DashboardFilterBar** on the Dashboard:
  - Subject picker: ``<select>`` populated from the full subjects
    tree.
  - Tag chip cloud: every user tag, click-to-toggle.
  - Filter state lives in the URL query string
    (``?subject=<id>&tag=<id>&tag=<id>``) so the page is
    bookmarkable and shareable.
  - "Matching projects (N)" list below the controls; clicking
    an entry sets it as the active projectId and bumps a
    version counter so the per-project widgets (radar,
    timeline, counter) re-fetch against the new project.
- AND across criteria + AND across multiple selected tags. The
  filter index is built once per mount via parallel per-project
  ``listSubjects`` + ``listTags`` calls.

### Bundled: PluginForge ^0.8.0 → ^0.9.0

Not part of the Phase 22 plan; dependency hygiene shipped in
the same release. v0.9.0 is the long-deferred hard-filter
transition for the v0.7.0 ``target_application`` work:
plugins without ``target_application`` are now REJECTED at
activation on hosts that declare ``app_id``. All 7 of our
plugins have ``target_application = "adaptive_learner"`` since
v1.7.0, and the host's ``PluginManager(app_id="adaptive_learner")``
constructor has been in place since the v1.7.0 hardening
round, so the upgrade is transparent — no plugin changes,
no startup regressions, full test suite green.

v0.9.0 also adds lifecycle visibility (additive, no breaking
change): ``PluginState.activated_at`` / ``.last_config_change``
/ ``.source`` UTC timestamps; ``PluginManager.inspect_plugin
(name)`` aggregator returning a ``PluginInspection`` snapshot
of state + config + health + hooks + routes + identity;
``on_plugin_activated`` / ``on_plugin_deactivated`` /
``on_config_refreshed`` event hooks. We don't consume these
yet — a future Settings → Plugins panel can render the new
fields without further code changes in pluginforge.

The v0.7.0 deprecation warning text for plugins without
``target_application`` is retired in v0.9.0; ``DiscoveryResult.errors``
no longer carries those warnings. Consumers filtering
``severity == "warning"`` and ``phase == "identity_check"``
will see no such entries on the v1.9.0 backend.

### 22F — Onboarding integration

- **Subject suggester**: as the user types in the Topic field, a
  client-side fuzzy matcher
  (``lib/subjectSuggest.ts``) scores every Subject against the
  typed text and surfaces the top-5 with full ancestor paths
  ("Languages > Spanish > Grammar"). Click-to-toggle chips.
- **Tag input**: comma-separated freeform names; the submit
  handler parses, creates (handling the 409 case for
  already-existing names), and assigns.
- Both run as soft-fail steps AFTER project creation. The user
  never gets trapped between project-create and the next page
  by a taxonomy assignment failure.

## Migration

No breaking changes at the UI or API layer. Existing devices
running v1.8.0 upgrade transparently:

- Alembic migration 0008 adds the four new tables on first
  startup.
- Dexie schema v6 upgrade is a clean add (no data migration
  needed; previously-stored rows are untouched).
- Subject seeding runs the first time the v1.9.0 backend starts
  against a fresh DB. Existing users see the seed nodes appear
  in the SubjectBrowser; their existing projects are untouched
  until they explicitly assign a subject.

Devices on v1.9.0 paired to a v1.8.0 backend will see push
requests for the four new sync tables return "Unknown sync
table" ValidationErrors. Upgrade the backend before the
phones — same release rule as v1.8.0.
