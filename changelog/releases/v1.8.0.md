# Adaptive Learner v1.8.0

**Released**: 2026-05-20

Phase 21 — **Sync Gaps: step_evaluations + session_notes + i18n
keys.** Closes the v1.0.0 sync-surface gaps that excluded
``step_evaluations`` (Dexie/backend column-name divergence) and
``session_notes`` (append-only classification didn't reflect the
mutable UI). Adds ``imported_conversations`` +
``imported_messages`` (Phase 12 chat-history surface) to sync.
Moves every ``sync.*`` UI string from inline ``t(key, "fallback")``
args to the 8 backend YAML catalogs. Closes BL-05 and BL-06.

Also bundled (not part of Phase 21 plan, dependency hygiene):
PluginForge ^0.7.0 → ^0.8.0 upgrade.

## Added

### 21A — step_evaluations on the sync surface

- Dexie schema v3: ``step_evaluations.suggested_step`` →
  ``to_step``, ``created_at`` → ``evaluated_at``. Existing
  rows back-fill with the backend semantics
  (``to_step = applied ? suggested_step : from_step``).
  Dexie-local ``duration_seconds`` stays as a UI-only column
  excluded from the sync payload.
- Frontend ``SYNC_TABLES`` gains ``step_evaluations`` with
  ``timestampField: "evaluated_at"``, ``appendOnly: true``.
- The backend ``TABLES`` entry was already there since the
  step-evaluator plugin shipped; this release made the Dexie
  side match.

### 21B — session_notes promoted from append-only to mutable

- Backend Alembic migration 0006: ``session_notes.updated_at``
  column added, back-filled from ``created_at``. Three-step
  migration (add nullable → back-fill → enforce NOT NULL) so
  SQLite's NOT-NULL constraint doesn't reject the ALTER.
- ``SessionNote`` model + ``SessionNoteOut`` schema expose
  ``updated_at``; SQLAlchemy's ``onupdate=_utcnow`` bumps the
  timestamp on every write.
- Dexie schema v4: ``session_notes.updated_at`` added,
  back-filled from ``created_at`` mirroring the Alembic
  back-fill. Index switches to ``updated_at``.
- Backend ``TABLES["session_notes"]`` flips to
  ``append_only=False, timestamp_field="updated_at"``. The
  conflict-resolution layer (existing since v1.0.0) handles
  ``session_notes`` like any other mutable row; the new
  ``test_invokes_the_conflict_resolver_when_a_session_notes_push_collides``
  test pins the resolver path end-to-end.

### 21C — sync i18n strings migrated to YAML catalogs

- 62 unique ``sync.*`` keys collected across SyncSection,
  SyncConflictDialog, QRScannerModal, and QRImageUpload.
- ``backend/config/i18n/en.yaml`` + ``de.yaml``: hand-authored
  canonical EN and hand-translated DE (real umlauts per the
  lessons-learned rule, no ae/oe/ue ASCII folding).
- ``{es,fr,el,pt,tr,ja}.yaml``: EN-passthrough per the BL-06
  convention — the catalog STRUCTURE matches across all 8
  languages even when native translations are pending a
  BL-11-style sweep.
- 63 call-site ``t(key, "fallback")`` args stripped from
  components → ``t(key)`` only.
- ``frontend/src/i18n/fallbacks.ts`` gains a ``sync:`` block
  in all 5 first-paint catalogs (de, en, es, fr, el) so the
  app never renders raw ``sync.foo`` keys if the backend i18n
  endpoint hasn't responded yet.

### 21D — imported_conversations + imported_messages on the sync surface

- Backend Alembic migration 0007: ``imported_messages.created_at``
  added, back-filled from parent ``imported_conversations.imported_at``
  via correlated subquery. Same three-step nullable-then-NOT-
  NULL pattern.
- New backend sync scope ``via_imported_conversation`` in
  ``_scoped_query`` joining ``imported_messages →
  imported_conversations.user_id`` for per-user filtering.
- Dexie schema v5: ``importedMessages.created_at`` added,
  back-filled by walking each row's parent conversation. The
  write path in ``dexieStorage.imports.create`` sets
  ``created_at = conv.imported_at`` for every newly-imported
  message.
- Both tables classified APPEND-ONLY. The ``analyzed`` flag and
  ``analysis_result`` blob are NOT updated post-sync; each
  device runs its own analysis to avoid pushing the heavy AI
  roundtrip over the wire.
- Frontend ``SYNC_TABLES`` gains both entries.

### 21E — Sync surface audit

- New backend test file ``test_sync_surface_audit.py`` with
  6 invariants:
  - Every SQLAlchemy domain model is in ``ALL_SYNC_TABLES``
    (and vice versa).
  - ``TABLES`` count matches the SQLAlchemy model count
    (16 each).
  - Append-only vs mutable classification matches the spec
    table (8 append + 8 mutable).
  - Every ``TableSpec.model`` references a real SQLAlchemy
    class with the right ``__tablename__``.
  - Every ``timestamp_field`` is a real column on the model.
  - Every entry in ``columns`` tuple references a real column.
- New frontend ``SYNC_TABLES — surface audit`` describe block
  with 3 invariants mirroring the backend (table coverage,
  append-only classification, timestampField non-empty).

## Notes

- Backend Alembic migrations 0006 + 0007 apply transparently
  in the FastAPI lifespan via ``init_db()``. Production
  upgrade: just bump the version and restart; existing data
  is back-filled in place.
- Dexie schema v3 + v4 + v5 upgrades are idempotent — re-
  opening the database after the version bump runs the
  upgrade callbacks once; subsequent opens skip them.
- The conflict-resolution path for session_notes uses the
  same ``POST /api/sync/resolve`` endpoint as users /
  projects / etc. No new endpoint shipped; the existing
  layer just sees session_notes as another mutable table.
- The i18n migration is a structural change with no
  functional impact for the user: every string still
  renders the same text. The benefit is centralised
  translation (one place to edit per language) and a clear
  contract for future BL-11 native-translation work.

## Migration

No breaking changes at the UI or API layer. Existing devices
running v1.7.0 can pair to a v1.8.0 backend; the new sync
tables silently start syncing on the first run after upgrade.

Devices on v1.8.0 paired to a v1.7.0 backend will see push
requests for the new tables return a "Unknown sync table"
ValidationError. Upgrade the backend before the phones.

BL-05 + BL-06 + BL-04 (already closed in v1.7.0) all archive
out of P0 now. The next P0 candidates are BL-03 (pluginforge-
app-template repo) and the v1.8.0-tier follow-ups documented
in ROADMAP.md.
