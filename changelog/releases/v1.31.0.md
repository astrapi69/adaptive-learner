# Adaptive Learner v1.31.0

**Released**: 2026-05-27

Phase 46 sub-phases E-F-G — **Gamification Integration +
LessonProgress↔LearningSession Unification + Docs**
(EXP-007 / P-129). Closes Phase 46 — the second half of the
original spec that v1.30.0 deliberately split. With v1.31.0
shipped, content lesson completions now feed the existing
XP / streak / badge / ProgressCommit machinery
**transparently** via a pseudo-project unification layer
that needed zero new hookspec.

## Why this release

v1.30.0 closed the element-level error-tracking + SRS loop
("the app remembers which word you struggled with and
schedules it for review"). But lesson completions still
stopped at the per-lesson summary screen — they didn't
contribute to streak heatmaps, didn't award XP, didn't
trigger the existing badge predicates, didn't write a
``ProgressCommit``. A user studying with content lessons
had no way to see their work in the same surfaces that
already aggregated chat sessions.

v1.31.0 closes that gap with the unification decision that
was confirmed (and deferred) at v1.30.0 decision time:
**D1 lazy pseudo-project + D5 reuse on_session_complete**.
When a content lesson completes, the lesson service:

1. Finds-or-creates a per-user "Content Lessons"
   pseudo-project (``LearningProject.kind="content"``,
   created lazily on first completion).
2. Writes a ``LearningSession`` row with
   ``method="content"`` (the new D2 7th method value).
3. Fires the existing ``on_session_complete`` pluggy
   hook — the gamification + tracking plugins' existing
   handlers run as if it were a chat session.

The dispatch in the gamification plugin's
``on_session_complete`` then routes ``method="content"`` to
a new lesson-specific XP formula (30 base + 10/star + 20
first-attempt 3-star), while chat methods stay on the
unchanged chat formula.

The result: lessons now fill the streak heatmap, award XP,
trigger four new lesson-specific badges, and write
ProgressCommit rows the same way chat sessions always have
— **without a single new hookspec**.

## What changed

### Added

#### Sub-phase 46F.1 — Schema change

- ``LearningProject.kind`` column (``String(32)``,
  ``server_default="standard"``) with constants
  ``LEARNING_PROJECT_KIND_STANDARD`` /
  ``LEARNING_PROJECT_KIND_CONTENT`` /
  ``LEARNING_PROJECT_KINDS`` following the
  ``SESSION_NOTE_KINDS`` pattern from Phase 42.
- Alembic ``0020_learning_project_kind`` via
  ``batch_alter_table`` + ``add_column``
  (SQLite-safe). Existing rows back-fill to "standard".
- Sync surface picks up ``kind`` so the column
  round-trips through ApiStorage ↔ DexieStorage in
  both directions.
- ``LearningProjectOut`` schema exposes ``kind`` with a
  ``"standard"`` default for pre-migration responses.
  Create / Update / CreateBody schemas intentionally do
  NOT expose ``kind`` — the field is set only by the
  lesson service's pseudo-project path, never from
  user input.

#### Sub-phase 46F.2 — Pseudo-project + LearningSession write

- New ``app/services/lesson_session_unification.py``
  module:
  - ``find_or_create_content_pseudo_project(db, user_id)``
    — idempotent lookup, creates on miss
  - ``record_lesson_completion_session(db, ...)`` —
    writes ``LearningSession`` + fires
    ``on_session_complete`` via ``manager._pm.hook``
- ``app/services/lesson_progress.py`` upsert hook fires
  the unification when a row flips ``in_progress`` →
  ``completed``. Wrapped so a unification failure cannot
  mask the lesson completion the user already saw.

#### Sub-phase 46E.1 — Lesson XP rule

- ``xp_service.compute_stars(correct, total)`` — 0-3
  band projection. Mirrors frontend's ``computeStars``
  (same 50% / 75% / 90% thresholds).
- ``xp_service.calculate_lesson_session_xp(*, stars,
  first_attempt, streak_days)`` — pure calculator. 30
  base + 10/star + 20 first-attempt-3-star + +25%/day
  streak multiplier capped at 7 days.
- ``xp_service._is_first_attempt(db,
  lesson_progress_id)`` — reads ``step_results`` JSON,
  returns True iff every step has ``attempts == 1``.
- ``xp_service.award_xp_for_lesson_session(db, *,
  session)`` — persistence wrapper.
- Dispatch in ``GamificationPlugin.on_session_complete``:
  ``method == "content"`` → lesson formula; otherwise
  → existing chat formula unchanged.

#### Sub-phase 46E.2 — Four new badges

- ``first_lesson`` (getting_started, ``book-open``):
  >= 1 completed ``LessonProgress``.
- ``lessons_10`` (depth, ``book-open``): >= 10 completed.
- ``three_star_streak`` (consistency, ``star``): the
  three most-recent completed lessons all earn 3 stars.
- ``review_master`` (depth, ``repeat``): >= 50
  ``ElementError`` rows with ``mastered=True``.

Catalog count: **24 → 28**. All four predicates land in
``badge_service._EVALUATORS`` symmetrically with their
YAML entries. i18n: 4 badges × 8 catalogues × 2 keys =
64 native translations (DE uses real umlauts).

#### Sub-phase 46F.3 — Frontend project-list filter

- ``LearningProject`` type gains ``kind: "standard" |
  "content"`` with pre-v1.31.0 wire fallback.
- New ``frontend/src/lib/learning-project.ts`` with
  ``isStandardProject`` + ``filterStandardProjects`` as
  the single source of truth.
- Applied in: ``DashboardFilterBar.tsx``,
  ``ExportSection.tsx``, ``Anki.tsx``.
- ``LearningRepoSettings`` not filtered (single-project
  prop, never lists). ``Onboarding`` not filtered
  (creates only).
- ``DexieStorage.rowToProject`` back-fills
  ``kind="standard"`` for pre-migration rows;
  ``projects.create`` always sets ``kind="standard"``
  in Dexie mode (Dexie users can't trigger the lazy-
  create unification path because there's no backend
  hook to fire).

### Changed

- ``GamificationPlugin.on_session_complete`` dispatches
  on ``session["method"]`` between the lesson formula and
  the chat formula. Existing chat-session tests stay
  green (125 XP for first-method-deductive session
  unchanged).
- ``LessonProgress.upsert_progress`` now also writes a
  ``LearningSession`` row on the in_progress→completed
  flip. Existing behaviour unchanged for the step-update
  path.

### Decisions confirmed in this release

- **D1 (lazy pseudo-project)**: created on first lesson
  completion, never seeded during onboarding. One per
  user.
- **D2 (``method="content"`` as 7th value)**: cleanest
  option per the handover; most code iterates the method
  enum and picks it up transparently.
- **D5 (reuse on_session_complete, no new hookspec)**:
  the gamification + tracking plugins' existing handlers
  fire for content sessions via dispatch on ``method``.
- **Badge thresholds + XP formula**: shipped as spec'd
  (10 lessons, 50 mastered, 3-consecutive-3-star;
  30 base + 10/star + 20 first-attempt-3-star). Tuning
  deferred until real usage data exists.

## Upgrade notes

- **Alembic ``0020_learning_project_kind``** adds the
  ``learning_projects.kind`` column. A fresh
  ``make dev`` picks it up automatically; deployed
  backends should run ``alembic upgrade head``. Existing
  ``learning_projects`` rows back-fill to ``"standard"``
  via the ``server_default``.
- **No new Dexie schema bump.** ``LearningProjectRow``
  gains an optional ``kind`` field but the existing
  schema v18 from v1.30.0 carries forward unchanged
  (Dexie's free-text rows accept the new field
  transparently).
- **No breaking changes** to existing routes, schemas,
  or storage shapes. The ``LearningProject.kind`` field
  is additive; consumers that don't know about it keep
  working.
- **Dexie-mode lesson completions** still write
  ``LessonProgress`` and ``ElementError`` rows but
  **don't** fire the unification path (no backend, no
  hookable). Lessons still trigger review-queue
  scheduling; XP / badge awards from lesson completions
  are API-mode-only by deliberate scope. A future
  release will close this gap by porting the XP rule to
  the storage abstraction.
