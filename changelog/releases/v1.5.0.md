# Adaptive Learner v1.5.0

**Released**: 2026-05-20

Phase 18 — **Async AI Calls + Performance.** At the cycle
boundary (step 6 → 7), the message route now fires step-evaluation
and topic-transition concurrently via ``asyncio.gather`` instead
of sequentially, cutting wall-clock latency by ~T₂ at the
critical auto-loop moment. Async SQLAlchemy foundation lands as
infrastructure for future async routes. Per-message timing
metrics expose the latency breakdown to the frontend.

## Added

### 18A — Async SQLAlchemy foundation

- New ``async_engine`` + ``AsyncSessionLocal`` + ``get_async_db``
  in ``backend/app/database.py``, alongside the existing sync
  setup. Additive — no breakage to any existing sync route.
- ``_async_database_url`` translates ``sqlite:///...`` to
  ``sqlite+aiosqlite:///...`` so the same connection string
  serves both engines.
- ``aiosqlite`` dependency added.
- 6 new pytest cases in ``test_async_database.py``.

### 18B — Async AI provider hooks

- New ``ai_complete_async`` hookspec — additive, no provider
  plugin needs to implement it yet.
- ``call_ai_complete_async`` helper in
  ``adaptive_learner_session/ai_orchestration.py`` prefers the
  async hook when any plugin registered it AND falls back to
  the sync hook wrapped in ``asyncio.to_thread`` otherwise. The
  thread fallback is what makes ``asyncio.gather`` deliver real
  parallelism on existing sync provider plugins.
- ``evaluate_step_async`` + ``evaluate_topic_transition_async``
  wrappers on top of the existing dataclass APIs.
- Parallel-overlap regression test: two evaluators sleeping 0.1s
  each must complete in <0.18s via ``asyncio.gather`` (proves
  real overlap, not sequential).
- 5 new pytest cases in ``test_async_ai.py``.

### 18C — Parallel evaluation calls

- At the step 6 → 7 transition, the session message route fires
  step-evaluation and topic-transition concurrently inside an
  ``asyncio.run`` block. Other steps stay on the sequential
  path (cheap; topic-transition is only pedagogically relevant
  at the cycle boundary).
- ``async_evaluation: true`` config flag in
  ``config/plugins/session.yaml``. ``asyncio.run`` failures
  cleanly fall back to the sequential path.
- The parallel block invokes async code from the sync route via
  ``asyncio.run`` so the DB session stays sync — no async DB
  migration required at the route layer.

### 18D — Streaming learning response

- Deferred. The user's spec marked this sub-phase optional; the
  large rewrite of three provider plugins + the chat UI is
  scoped for a future minor version.

### 18E — Performance metrics

- New ``_TimingsOut`` block on the ``/message`` response:
  ``{learning_ms, evaluation_ms, topic_transition_ms, total_ms,
  parallel_saved_ms}``. Per-call markers wrap the AI roundtrips
  with ``time.monotonic``; the parallel block (18C) attributes
  the gather wall-time symmetrically to both evaluators AND
  captures ``parallel_saved_ms``.
- ``MessageTimings`` type added to the frontend domain types.

## Notes

- Frontend stays UNCHANGED for the non-streaming endpoint: same
  ``/message`` response shape, with optional new fields the UI
  can ignore.
- Sync routes (users, projects, settings, etc.) stay sync; only
  the session hot path benefits from the async work.
- Backward compatible: the sync ``ai_complete`` hook still
  works; ``ai_complete_async`` is additive.
- Each parallel call has independent error handling — one
  failure does not break the other. Failure of the entire
  parallel block falls back to the sequential path.
- Learning response is NEVER run in parallel with evaluation;
  evaluation reads the learning response from the transcript.
