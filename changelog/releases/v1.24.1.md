# Adaptive Learner v1.24.1

**Released**: 2026-05-23

Phase 40 — release-automation hardening. Six atomic commits
that align Adaptive Learner's release tooling with Bibliogon's
4-Tier model: package-lock propagation, open-set version-literal
discovery, advisory WARN wiring, aggregate `make release-*`
targets, 4-Tier architecture documentation, and a plugin
refactor that unblocks the verify chain.

No user-visible runtime changes. No database schema changes.
No new runtime dependencies. Patch release.

## Why this release

v1.24.0 shipped a fully-functional but partially-automated
release flow: every release re-derived "which files carry the
version, in what order do I edit them, how do I tag" from the
release-workflow rule. Two real-world drift incidents (the
frontend/package-lock.json `"version": "1.23.2"` literal sat
stale through the v1.24.0 release; the plugin static-literal
pattern silently blocked `verify_version_pins.sh` from
returning clean) made the gap concrete enough to address as
its own release.

Bibliogon's release tooling (the upstream project this
infrastructure originally came from) had since closed the same
gaps over its own release cycles. Phase 40 ports the
battle-tested pieces back without copying their domain-specific
plugins.

Full Phase 40 audit + tier table in commit `824a5bc`'s pre-flight
report (re-runnable from `docs/development/release-automation.md`
"Phase 40 audit history" footer).

## What changed

### A — package-lock.json handling (commit `824a5bc`)

`scripts/sync_versions.py` gains `update_package_lock_version`.
Surgical regex on the first 2 `"version":` lines of
`frontend/package-lock.json` (top-level metadata + the
`packages[""]` root entry), with JSON-parse validation before
any mutation. Subsequent `"version":` lines are nested
dependency entries and stay untouched.

Same commit fixes the actual drift the new handler caught:
`frontend/package-lock.json` was sitting at `1.23.2` while the
canonical pin was at `1.24.0`. v1.24.1 ships the lock-file at
the correct `1.24.1` from the first time anyone runs
`npm install`.

### B — Open-set version-literal discovery (commit `e8a7f3d`)

New `scripts/discover_version_literals.sh`. Greps for
version-assignment patterns (`version = "..."`, `"version":
"..."`, `__version__ = "..."`, `APP_VERSION = "..."`,
`CFBundle*: "..."`) across the whole repo, then subtracts the
known-target list (sync-versions Tier-1/2 + Tier-4 manual
content + per-plugin static files + sentinel fallbacks + test
fixtures). Anything left is a discovery candidate — either a
new sync-target or a legitimate one-off literal.

Closes the closed-set blind spot the regression detectors
above couldn't see: a future feature adding a NEW file with a
version literal slips past every existing gate.

Exit code always 0 (advisory only, not a gate).

### C — Discover script wired into verify chain (commit `6a8ebe5`)

`scripts/verify_version_pins.sh` gains a non-fatal WARN block
at the end of its validation chain that runs
`discover_version_literals.sh` and indents the output under a
WARN header. Discovery findings do NOT increment the error
count and do NOT block tagging.

### D — Aggregate `make release-*` targets (commit `4bebb52`)

Seven new Makefile targets compose existing tools for the
mechanical release-workflow.md steps:

- `make release-state` (Step 1): latest tag + commits since +
  diff stat + canonical version.
- `make release-outdated` (Step 4b): `poetry show --outdated` ×
  backend + launcher; `npm outdated` × frontend.
- `make release-test` (Step 5): `make test` + `npm run build`
  + `npm run test` (vitest) + `sync-versions-check` +
  `verify-plugin-locks`.
- `make release-build` (Step 6): conditional backend
  `poetry build` (skipped iff `package-mode=false`) +
  frontend `npm run build`.
- `make release-discover` (Step 4 supplement): open-set
  literal discovery with verbose output.
- `make release-tag VERSION=X.Y.Z` (Step 7): pre-tag
  `verify_version_pins.sh` + `git tag -a` + push main +
  push tag.
- `make release-publish VERSION=X.Y.Z` (Step 8):
  `gh release create` from
  `changelog/releases/vX.Y.Z.md`.

`VERSION` is required on `release-tag` + `release-publish` via
Makefile `ifndef` so a typo'd invocation fails immediately
with a clear message rather than tagging an empty string.

### E — 4-Tier release-automation architecture doc (commit `082abb9`)

New `docs/development/release-automation.md`:

- **Tier 1** — canonical source (`backend/pyproject.toml`,
  hand-edit only).
- **Tier 2** — auto-propagated by `make sync-versions`
  (17 derived locations).
- **Tier 3** — runtime-derived (`tomllib` parse,
  `importlib.metadata`, Vite `define`, PyInstaller injection).
- **Tier 4** — manual content (release narrative, changelog
  prose).

Also adds the "Adding a new propagated file" and "Adding a new
version-string location discovered in the wild" extension
recipes for future maintainers.

`.claude/rules/release-workflow.md` gains an "Architecture
reference" cross-link near the top + `frontend/package-lock.json`
in the "DO NOT EDIT" derivation table.

### F — Plugin importlib.metadata refactor (commit `ca939c9`)

Three plugins (gamification, anki, notebooklm) carried a static
`__version__ = "1.24.0"` literal that `verify_version_pins.sh`
flagged as a "hardcoded Python __version__ literal" regression.
The other seven plugins already used the `importlib.metadata`
derivation pattern with a `"0.0.0+unknown"` sentinel fallback.

Refactored the three holdouts to match. All ten plugins now
follow the same pattern; `verify_version_pins.sh 1.24.1` exits
0 with "All canonical version sources match 1.24.1.
Derivations clean."

The editable-install caveat (`importlib.metadata` reads the
dist metadata at install time and doesn't refresh on
pyproject.toml bumps unless `poetry install --sync` runs)
applies to all ten plugins equally; v1.24.1 does NOT make this
worse, it makes the surface consistent.

## Migration

No database schema changes. No production runtime dependency
bumps. No frontend bundle changes. Existing user storage works
unchanged. Existing dev databases work unchanged.

Internal: `frontend/package-lock.json` ships at `1.24.1`
already (v1.24.0 left it stale at `1.23.2`). Anyone running
`npm install` against the v1.24.1 tree will see the lock
update on first install as a side effect, not because anything
runtime changed.

## What's next

- Future contributors adding a new propagated file follow the
  recipe in `docs/development/release-automation.md`.
- Open-set discovery runs on every tag push via
  `release-gate.yml` (advisory WARN; does not block).
- `make release-*` targets are now the documented path for the
  next release; release-workflow.md remains the human-side
  checklist.
